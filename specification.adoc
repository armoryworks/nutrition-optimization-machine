[#_abstract]
== Abstract

This document outlines the business analysis and functional specifications for key components of the Nutritional Optimization Machine (NOM) program. It synthesizes the requirements and functionalities identified and developed during the initial phases of the project, particularly focusing on user onboarding, dietary restriction management, data privacy compliance, and foundational system architecture. This revision (2.5) expands the specification to include a comprehensive recipe and ingredient management system, a site-wide content curation workflow, and a user-to-user communication platform. The purpose of this specification is to provide a common understanding for stakeholders, developers, and testers regarding the system's current and planned capabilities, its intended user interactions, the data privacy requirements, and the underlying business rules it enforces.

[#_introduction]
== Introduction

[#_project_vision]
=== Project Vision

The overarching vision for the Nutritional Optimization Machine (NOM) program is to empower individuals and families to achieve their health and wellness goals through highly personalized, intelligent nutritional planning. We aim to move beyond generic diet advice by deeply understanding individual dietary needs, preferences, and medical restrictions, and then leveraging this data to optimize meal plans. This vision is supported by a robust, community-driven content ecosystem where users can create, share, and refine recipes and ingredients under the guidance of a structured curation process, fostering a collaborative and trustworthy nutritional environment. Ultimately, NOM seeks to simplify healthy eating, make it more accessible, and foster collaborative dietary management within groups (families, teams, etc.).

[#_executive_summary]
== Executive Summary

The NOM program aims to provide users with tools for personalized nutritional planning. The initial focus has been on establishing a robust user onboarding process that not only collects essential user information but also intelligently infers and manages dietary restrictions. A flexible questionnaire system, backed by a structured data model and secure API, forms the core of this initial user interaction. Furthermore, the system is designed to support the future integration of users into existing nutritional plans via invitation, laying the groundwork for collaborative features.

This specification introduces the next major phase of development, focusing on user-generated content and administrative oversight. This includes a full lifecycle for recipe and ingredient management, from author creation to a formal curation process managed by site-wide administrators. A versioning system will ensure that curated content remains stable and public while authors iterate on new versions. This phase also introduces a direct user-to-user and admin-to-user communication system to support the curation feedback loop and general community interaction.

== User Roles & Personas

The following primary user roles and system actors have been identified and considered in the developed functionalities:

[cols="25%,75%",options="header"]
|===
| Role | Description

| *New User / Prospect*
| An individual who has just registered or is in the process of initial account setup, requiring guidance through onboarding questions and initial privacy consent.
| *Authenticated User*
| A registered and logged-in user of the system who can interact with various features, including submitting personal information and participating in plans.
| *Plan Administrator*
| An authenticated user who creates and manages nutritional plans, and can invite others to join.
| *Plan Member*
| An authenticated user who participates in an existing nutritional plan.
| ***Recipe Author*** (NEW)
| An authenticated user who can create, edit, and manage their own recipes and custom ingredients, and submit them for curation.
| ***Site-Wide Admin*** (NEW)
| An authenticated user with the `CanManageCuration` claim. This role is responsible for reviewing, approving, rejecting, and providing feedback on user-submitted recipes and ingredients. They can communicate with any user.
| ***User Role Manager*** (NEW)
| An authenticated user with the `CanManageUserRoles` claim. This role can grant or revoke the `CanManageCuration` and `CanManageUserRoles` claims for any user in the system.
| *System*
| An automated entity responsible for background processes, such as the automatic inference and recording of dietary restrictions based on user input, ensuring data integrity and auditability.
| *Privacy Officer*
| A designated role responsible for overseeing data protection compliance, handling user privacy rights requests, and maintaining compliance documentation.

== Functional Requirements

[#onboarding-requirements]
=== User Onboarding & Profile Completion

.Objective
To efficiently collect essential user data and personal preferences immediately following account registration, establishing a foundational user profile.
[cols="20%,80%",options="header"]
|===
| ID | Requirement

| *FR-1.1*
| *Multi-Step Onboarding Workflow*: The system shall present a guided, multi-step onboarding process, composed of reusable domain-specific edit components.
| *FR-1.2*
| *Core Profile Data Collection*: The initial step shall collect essential personal profile details for the newly registered user.
| *FR-1.3*
| *Health Attributes Collection*: The workflow shall include an optional step for collecting health-related attributes.

| *FR-1.4*
| *Iterative Restriction Collection*: The workflow shall guide the user through defining dietary restrictions. This step will repeat for each major 'Restriction Type' (societal/religious/ethical, allergies/medical, personal preferences).

| *FR-1.4.1*
| *Restriction Scope Selection*: For each identified restriction, the user shall be prompted to specify if it applies to everyone on the plan or to specific individuals.
| *FR-1.4.2*
| *Individual Restriction Assignment*: If a restriction applies to specific individuals, the user shall be provided with a selection list to designate which person(s) (including themselves) are affected.
| *FR-1.5*
| *Workflow Control Navigation*: Each step in the onboarding process shall be wrapped with a user interface providing "Next", "Back", "Skip" (where optional), "Yes", "No", and "Submit" (where applicable) buttons to control navigation and data submission.
| *FR-1.6*
| *UI-Only Workflow Steps*: Certain steps may be purely for workflow control, collecting user decisions without immediate API interaction, influencing subsequent steps.
| *FR-1.7*
| *Final Onboarding Data Submission*: Upon completing all required onboarding steps, a summary shall be presented, allowing the user to review and submit all collected PersonEntity, PersonAttributeEntity, and RestrictionEntity data in a single operation.
| *FR-1.8*
| *Multi-Participant Onboarding (Conditional)*: Support for adding multiple participants to a plan with individual preference collection.
|===

[#restriction-requirements]
=== Dietary Restriction Management & Inference

.Objective
To automatically identify and record dietary restrictions based on user responses during onboarding, streamlining the personalization of nutritional plans.
[cols="20%,80%",options="header"]
|===
| ID | Requirement

| *FR-2.1*
| *Restriction Data Capture*: The system shall capture detailed dietary restrictions, including categorization into "societal, religious, or ethical practices", "allergies and medical restrictions", and "personal preferences".
| *FR-2.2*
| *Specific Restriction Details*: Capture detailed restriction information across multiple categories.

| *FR-2.3*
| *Person- or Plan-Level Association*: Restrictions collected during onboarding must be associable with either specific individuals (PersonEntity) or the entire PlanEntity, as determined by FR-1.4.1.
| *FR-2.4*
| *Prevention of Duplicates*: The system shall prevent the creation of duplicate Restriction records for the same Person (or Plan, if applicable) and the same Restriction Type.
| *FR-2.5*
| *Auditability*: All created Restriction records shall include audit information, indicating their creation time and the creating Person (or System).

[#_specific_restriction_details]
==== Specific Restriction Details

[dlist]
*Societal/Religious/Ethical*::
Capture selections from predefined lists (e.g., Kosher, Vegan), fasting schedules, and mandatory inclusions (searchable list of curated ingredients).
*Allergies/Medical*::
Capture selections from predefined allergy lists (e.g., Peanuts, Dairy), Yes/No for specific conditions (Celiac, Lactose Intolerance, Diabetes types, High Blood Pressure/Cholesterol, Gout, Anemia, Pregnancy), selections for gastrointestinal conditions (Crohn's, IBS), specific nutrient restrictions for kidney disease (sodium, potassium, phosphorus, protein, fluids), vitamin/mineral deficiencies (searchable list of micronutrients), and prescription interactions.
*Personal Preferences*::
Capture preferred spice levels, disliked ingredients (searchable list of curated ingredients), disliked textures, and preferred cooking methods.

[#recipe-management-requirements]
=== Recipe & Ingredient Management (IMPLEMENTED)

.Objective
To empower Recipe Authors to create, manage, and version their own recipes and custom ingredients.

[cols="20%,80%",options="header"]
|===
| ID | Requirement

| *FR-RM-1.1*
| *Recipe Creation*: An author shall be able to create a new recipe, providing a name, description, ingredients, and instructions (steps).
| *FR-RM-1.2*
| *Reuse-First Ingredient Workflow*: When adding ingredients to a recipe, the UI shall prioritize searching for and reusing existing ingredients.
| *FR-RM-1.3*
| *Custom Ingredient Creation*: The UI shall provide a secondary workflow for an author to create a new ingredient, including its nutritional data, if it does not already exist. This new ingredient will have a default `CurationStatus` of `NonCurated`.
| *FR-RM-1.4*
| *Recipe & Ingredient Dashboard*: An author shall have a dedicated dashboard (`RecipeAuthorDashboardComponent`) to view all their created recipes and ingredients, filterable by their `CurationStatus`.
| *FR-RM-1.5*
| *Recipe Modification & Deletion*: An author shall be able to modify or delete their `NonCurated` or `Rejected` recipes.
| *FR-RM-1.6*
| *Recipe Versioning*: If an author edits a `Curated` recipe, the system shall create a new version of that recipe with a `CurationStatus` of `NonCurated`. The original `Curated` version remains unchanged and publicly visible.
| *FR-RM-1.7*
| *Version Pre-population*: When creating a new version of an existing recipe, the creation form shall be pre-populated with all the data from the previous version.
| *FR-RM-1.8*
| *Ingredient Duplicate Prevention*: The system shall prevent creation of duplicate ingredients by implementing real-time duplicate checking in the ingredient creation modal, providing UI feedback and allowing users to select existing ingredients instead.
| *FR-RM-1.9*
| *Modal-Based Ingredient Creation*: Ingredient creation shall occur in a modal dialog that pre-populates the ingredient name from the search field, returns the created ingredient to the parent component, and automatically selects it in the recipe form.
|===

[#curation-requirements]
=== Content Curation Workflow (PARTIALLY IMPLEMENTED)

.Objective
To provide a robust system for Site-Wide Admins to review and manage user-submitted content, ensuring quality and consistency.

[cols="20%,80%",options="header"]
|===
| ID | Requirement

| *FR-CU-2.1*
| *Submission for Curation*: A Recipe Author shall be able to submit their `NonCurated` recipes and ingredients for curation, which changes their status to `PendingCuration`.
| *FR-CU-2.2*
| *Curation Queue*: Site-Wide Admins shall have access to a Curation Queue screen (`CurationQueueComponent`), displaying all content with a `PendingCuration` status.
| *FR-CU-2.3*
| *Queue Filtering & Sorting*: The Curation Queue shall be sortable by submission date and filterable by author and resubmission status.
| *FR-CU-2.4*
| *Curation Approval*: An admin shall be able to approve a submission, changing its status to `Curated`. This action allows for optional private notes (author-only) and public notes.
| *FR-CU-2.5*
| *Curation Rejection*: An admin shall be able to reject a submission, changing its status to `Rejected`. This action requires the admin to provide explanatory notes.
| *FR-CU-2.6*
| *Request for Revision*: An admin shall be able to request revisions from the author, changing the status to `RequiresRevision`. This action requires feedback notes.
| *FR-CU-2.7*
| *Curation Dependency Validation*: The system shall prevent a recipe from being approved (`Curated`) if it contains any ingredients that are not also `Curated`. The UI must inform the admin of this dependency.

.Purpose
Manages individual user accounts and associated personal profiles within the system.

[cols="20%,80%",options="header"]
|===
| Rule ID | Description

| *Rule-5.1.1*
| *Unique Identification*: Each Person record shall have a unique identifier.

| *Rule-5.1.2*
| *Account Creation*: Users must register with a unique email address and a password meeting minimum complexity requirements.

| *Rule-5.1.3*
| *Email Confirmation*: User email addresses should be confirmable to ensure validity and security.

| *Rule-5.1.4*
| *Password Security*: Users must be able to securely reset forgotten passwords and update existing passwords, requiring validation of their current identity.
| *Rule-5.1.5*
| *Two-Factor Authentication (2FA)*: Users can opt to enable 2FA for enhanced login security, which requires a one-time code from an authenticator app in addition to their password. The system must support the generation of shared keys and recovery codes.

| *Rule-5.1.6*
| *Invitation Code Uniqueness*: InvitationCodes associated with Person records (for inviting others to join a person-specific context, if applicable) must be unique.

[#_enhanced-import-quality-scoring]
===== Quality Scoring Algorithm

The enhanced import system implements a weighted quality scoring algorithm:

```
Quality Score = (DataPoints * 0.3) + (DataFreshness * 0.2) + (FoodType * 0.3) + (NameQuality * 0.2)
```

[dlist]
*DataPoints*::
- Number of supporting data points (higher = better quality)
- Minimum threshold: 1 data point
- Recommended threshold: 2+ data points
*DataFreshness*::
- Year of data acquisition (newer = better quality)
- Minimum threshold: 2010
- Recommended threshold: 2015+
*FoodType*::
- Foundation foods: 0.9 (highest quality)
- Survey foods: 0.7 (medium quality)
- Branded foods: 0.5 (lower quality)
*NameQuality*::
- Length and clarity of ingredient names
- Maximum length: 150 characters
- Filters out overly long, repetitive names

===== AI Enhancement Prompt Strategy

The AI enhancement system uses a carefully engineered prompt to ensure high-quality, recipe-friendly ingredient names:

[source,text]
----
You are a nutrition data specialist adjusting ingredient details for recipes that will be shared across multiple recipes. The enhancedName should be as simple as possible without inferring additional non-supplied details. The description should be comprehensive, but not add any non-inferrable details. If any brand names are in the original, they can be placed in the aliases, but should not be included in the produced Name or Description.

CRITICAL: If the original name contains nutritional modifiers like 'lean', 'low fat', 'low sodium', 'fat-free', 'reduced fat', 'light', 'nonfat', 'low-calorie', 'diet', 'lite', 'no salt added', 'fortified', '95% lean', '2%', 'whole fat', 'whole milk', 'skim', '1%', 'reduced sodium', 'sugar-free', 'unsweetened', 'enriched', 'organic', 'grass-fed', 'free-range', 'cage-free', 'hormone-free', 'antibiotic-free', etc., these MUST be retained in the enhanced name as they significantly affect nutritional values. IMPORTANT: If a specific percentage is given (like '95% lean', '90% lean', '85% lean', '80% lean'), the exact percentage MUST be retained in the enhanced name as it affects cooking characteristics and nutritional content. Examples: 'Beef, ground, 95% lean meat / 5% fat' should become '95% Lean Ground Beef', 'Beef, ground, 90% lean meat / 10% fat' should become '90% Lean Ground Beef', 'Milk, fluid, 2% milkfat' should become '2% Milk'.

Original: {ingredient.Name} - {ingredient.Description}

Respond with ONLY a JSON object containing enhancedName, enhancedDescription, and aliases array. No other text.
----

[#dev-learnings]
=== Key Development Learnings

[#_angular_development]
==== Angular Development

[dlist]
*AOT Compilation*:: Angular's AOT compiler is strict. Avoid complex JavaScript expressions directly in HTML template bindings. Move such logic into component TypeScript methods (getters or helper functions).
*Standalone Component Imports*:: Every standalone component must explicitly import all modules it directly uses in its `@Component({ imports: [...] })` array. Missing imports cause runtime errors.
*Data Flow Patterns*:: Be mindful of Angular's unidirectional data flow. Use `@Input` for data down, `@Output` for events up. Avoid direct child manipulation.
*Template Logic*:: Use getters in TypeScript for complex template logic (e.g., `filteredRestrictionsForCurrentPerson`). This resolved "Parser Error: Bindings cannot contain assignments" issues.
*Source Map Configuration*:: For debugging in Firefox/Chrome, ensure TypeScript and Angular configurations explicitly enable source maps. Add `"sourceMap": true` to `tsconfig.json` and configure development builds with proper source map settings.
*Form Validation*:: When working with complex forms (like recipe creation), ensure proper form validation by calling `updateValueAndValidity()` after dynamic changes and using `setTimeout` for async operations to ensure validation state is properly updated.
*Modal Data Flow*:: When using modals for data creation (like ingredient creation), ensure robust data extraction from modal results, handling both object and primitive return types, and properly updating parent component state.

[#_backend_development]
==== Backend Development

[dlist]
*API URL Management*:: Always double-check `apiUrl` constants in frontend services. These frequently need adjustment between local development and deployment environments.
*Interceptor Order*:: The order of `HTTP_INTERCEPTORS` in `app.config.ts` matters. Ensure `BearerInterceptor` runs before `ApiInteractionInterceptor`.
*Privacy Compliance*:: Always consider data minimization when adding new data collection points. Document the lawful basis for any new personal data processing.
*Authentication Scheme Configuration*:: When implementing Bearer token authentication, ensure both `IdentityConstants.BearerScheme` and `JwtBearerDefaults.AuthenticationScheme` are configured to handle different token types and prevent "No authentication handler is registered" errors.
*Authorization Policies*:: Configure authorization policies to support multiple authentication schemes using `AddAuthenticationSchemes()` to ensure compatibility with different token types.
*Entity Field Auditing*:: Regularly audit entity fields to identify and remove redundant or inappropriate fields (like `Instructions` string properties that duplicate `RecipeSteps` collections).
*Database Migration Safety*:: When removing fields from entities, ensure all references are updated in migrations, services, and controllers to prevent runtime errors during migration application.

[#_debugging_tips]
==== Debugging Tips

[dlist]
*Browser Caching*:: During frontend development, browser caching can cause issues. Clear browser cache or use "Incognito/Private" mode. `ng serve` usually handles this well.
*Clean Builds*:: For persistent issues, perform clean builds: `npm install`, delete `.angular` and `dist` directories, then rebuild.
*Service Scope Issues*:: Resolved `ServiceScopeFactory` reference errors in `Program.cs` by ensuring proper dependency injection configuration.
*Authentication Debugging*:: When debugging authentication issues, check both frontend token storage and backend authentication scheme configuration. Use browser dev tools to inspect token format and backend logs for authentication handler registration.
*Form Validation Debugging*:: For complex forms, add temporary debug panels to inspect form validity states and individual control validation. Use `console.log` to track form state changes and identify validation issues.
*Modal Data Flow Debugging*:: When debugging modal data flow, log both the modal result and the extracted data in the parent component to identify data transformation issues.
*Source Map Issues*:: If source files don't appear in browser debugger, check TypeScript and Angular configuration for source map settings, clear browser cache, and ensure development build is used.

[#conclusion]
== Conclusion

This specification provides a comprehensive overview of the Nutritional Optimization Machine (NOM) program's current implementation status and technical architecture. The system has evolved from a basic user onboarding platform to a sophisticated nutritional planning application with robust privacy compliance, user-generated content management, and administrative oversight capabilities.

Key achievements include:
- Complete authentication and authorization system with dual Bearer token support
- Full privacy compliance implementation with GDPR-compliant data subject rights
- Comprehensive recipe and ingredient management with modal-based creation and duplicate prevention
- Robust curation workflow with admin interface and type-safe status management
- Event-driven architecture with decoupled services for improved maintainability
- Material 3 theming and responsive design throughout the application

The technical implementation demonstrates best practices in both frontend and backend development, with particular attention to security, privacy, and user experience. The modular architecture supports future enhancements while maintaining code quality and consistency.

As the project continues to evolve, this specification serves as a living document that will be updated to reflect new features, architectural decisions, and implementation details.
