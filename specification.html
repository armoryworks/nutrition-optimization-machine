Abstract

This document outlines the business analysis and functional specifications for key components of the Nutritional Optimization Machine (NOM) program. It synthesizes the requirements and functionalities identified and developed during the initial phases of the project, particularly focusing on user onboarding, dietary restriction management, data privacy compliance, and foundational system architecture.

The purpose of this specification is to provide a common understanding for stakeholders, developers, and testers regarding the system’s current capabilities, its intended user interactions, the data privacy requirements, and the underlying business rules it enforces.

Introduction

Project Vision

The overarching vision for the Nutritional Optimization Machine (NOM) program is to empower individuals and families to achieve their health and wellness goals through highly personalized, intelligent nutritional planning. We aim to move beyond generic diet advice by deeply understanding individual dietary needs, preferences, and medical restrictions, and then leveraging this data to optimize meal plans. Ultimately, NOM seeks to simplify healthy eating, make it more accessible, and foster collaborative dietary management within groups (families, teams, etc.).

Executive Summary

The NOM program aims to provide users with tools for personalized nutritional planning. The initial focus has been on establishing a robust user onboarding process that not only collects essential user information but also intelligently infers and manages dietary restrictions. A flexible questionnaire system, backed by a structured data model and secure API, forms the core of this initial user interaction. Furthermore, the system is designed to support the future integration of users into existing nutritional plans via invitation, laying the groundwork for collaborative features.

Note
Current Development Status

  • User Onboarding (COMPLETE): The comprehensive, multi-participant user onboarding workflow is now fully implemented on both the frontend and backend. The system correctly prevents duplicate person records.

  • Privacy & Compliance Feature (COMPLETE): The system’s "privacy-by-design" architecture is fully implemented, including backend services and a complete frontend UI for managing data rights.

  • USDA FoodData Central Integration (COMPLETE): A dedicated console application, Nom.Import, has been created to handle the ETL (Extract, Transform, Load) process for the USDA FDC dataset. The application successfully populates the database with foundational ingredient and nutrient data.

  • Immediate Next Focus: Development will now focus on creating the backend API layer (RecipeOrchestrationService and RecipeController) to expose the imported food data to the frontend.

User Roles & Personas

The following primary user roles and system actors have been identified and considered in the developed functionalities:

Role Description

New User / Prospect

An individual who has just registered or is in the process of initial account setup, requiring guidance through onboarding questions and initial privacy consent.

Authenticated User

A registered and logged-in user of the system who can interact with various features, including submitting personal information and participating in plans.

Plan Administrator

An authenticated user who creates and manages nutritional plans, and can invite others to join.

Plan Member

An authenticated user who participates in an existing nutritional plan.

System

An automated entity responsible for background processes, such as the automatic inference and recording of dietary restrictions based on user input, ensuring data integrity and auditability.

Privacy Officer

A designated role responsible for overseeing data protection compliance, handling user privacy rights requests, and maintaining compliance documentation.

Functional Requirements

User Onboarding & Profile Completion

Objective

To efficiently collect essential user data and personal preferences immediately following account registration, establishing a foundational user profile.

ID Requirement

FR-1.1

Multi-Step Onboarding Workflow: The system shall present a guided, multi-step onboarding process, composed of reusable domain-specific edit components.

FR-1.2

Core Profile Data Collection: The initial step shall collect essential personal profile details for the newly registered user.

FR-1.3

Health Attributes Collection: The workflow shall include an optional step for collecting health-related attributes.

FR-1.4

Iterative Restriction Collection: The workflow shall guide the user through defining dietary restrictions. This step will repeat for each major 'Restriction Type' (societal/religious/ethical, allergies/medical, personal preferences).

FR-1.4.1

Restriction Scope Selection: For each identified restriction, the user shall be prompted to specify if it applies to everyone on the plan or to specific individuals.

FR-1.4.2

Individual Restriction Assignment: If a restriction applies to specific individuals, the user shall be provided with a selection list to designate which person(s) (including themselves) are affected.

FR-1.5

Workflow Control Navigation: Each step in the onboarding process shall be wrapped with a user interface providing "Next", "Back", "Skip" (where optional), "Yes", "No", and "Submit" (where applicable) buttons to control navigation and data submission.

FR-1.6

UI-Only Workflow Steps: Certain steps may be purely for workflow control, collecting user decisions without immediate API interaction, influencing subsequent steps.

FR-1.7

Final Onboarding Data Submission: Upon completing all required onboarding steps, a summary shall be presented, allowing the user to review and submit all collected PersonEntity, PersonAttributeEntity, and RestrictionEntity data in a single operation.

FR-1.8

Multi-Participant Onboarding (Conditional): Support for adding multiple participants to a plan with individual preference collection.

Multi-Participant Onboarding Details

ID Requirement

FR-1.8.1

Participation Inquiry: An optional UI-only step shall ask if additional people will participate in the plan.

FR-1.8.2

Participant Count: If affirmative, a subsequent UI-only step shall ask how many additional people will participate.

FR-1.8.3

Blank Name Slots: The system shall present blank name slots for the specified number of additional participants.

FR-1.8.4

Individual Preference Application: An optional UI-only step shall ask if individual preferences should apply to each person on the plan.

FR-1.8.5

Iterative Participant Onboarding: Step 1.4 (Iterative Restriction Collection) shall be reused and repeated for each additional person added to the plan, allowing the user to skip at any point during these repetitions.

Dietary Restriction Management & Inference

Objective

To automatically identify and record dietary restrictions based on user responses during onboarding, streamlining the personalization of nutritional plans.

ID Requirement

FR-2.1

Restriction Data Capture: The system shall capture detailed dietary restrictions, including categorization into "societal, religious, or ethical practices", "allergies and medical restrictions", and "personal preferences".

FR-2.2

Specific Restriction Details: Capture detailed restriction information across multiple categories.

FR-2.3

Person- or Plan-Level Association: Restrictions collected during onboarding must be associable with either specific individuals (PersonEntity) or the entire PlanEntity, as determined by FR-1.4.1.

FR-2.4

Prevention of Duplicates: The system shall prevent the creation of duplicate Restriction records for the same Person (or Plan, if applicable) and the same Restriction Type.

FR-2.5

Auditability: All created Restriction records shall include audit information, indicating their creation time and the creating Person (or System).

Specific Restriction Details

Societal/Religious/Ethical

Capture selections from predefined lists (e.g., Kosher, Vegan), fasting schedules, and mandatory inclusions (searchable list of curated ingredients).

Allergies/Medical

Capture selections from predefined allergy lists (e.g., Peanuts, Dairy), Yes/No for specific conditions (Celiac, Lactose Intolerance, Diabetes types, High Blood Pressure/Cholesterol, Gout, Anemia, Pregnancy), selections for gastrointestinal conditions (Crohn’s, IBS), specific nutrient restrictions for kidney disease (sodium, potassium, phosphorus, protein, fluids), vitamin/mineral deficiencies (searchable list of micronutrients), and prescription interactions.

Personal Preferences

Capture preferred spice levels, disliked ingredients (searchable list of curated ingredients), disliked textures, and preferred cooking methods.

Plan Invitation & Participation

Objective

To enable users to join existing nutritional plans through a secure invitation mechanism.

ID Requirement

FR-3.1

Invitation Code Input: The onboarding process shall include an optional step for users to input a unique invitation code.

FR-3.2

Plan Linking: If a valid invitation code is provided and the user successfully completes onboarding, the system shall link the user’s Person record to the corresponding Plan using a PlanParticipant entity.

FR-3.3

Role Assignment: Upon successful plan participation via invitation code, the PlanParticipant shall be assigned a default role (e.g., "Plan Member").

Authentication & Authorization

Objective

To secure system access and protect sensitive user data and functionalities.

ID Requirement

FR-4.1

Authenticated Access: Most API endpoints shall require a valid authentication token (e.g., JWT) for access, ensuring only authenticated users can perform actions or retrieve sensitive data.

FR-4.2

Anonymous Access for Onboarding: Specific public endpoints (e.g., initial user registration) shall be accessible without prior authentication to facilitate the initial user journey.

FR-4.3

User Registration: The system shall support user registration, creating new user accounts and associated Person records.

FR-4.4

User Login: The system shall support user login, issuing authentication tokens upon successful credential verification.

Data Privacy & Compliance

Objective

To ensure compliance with applicable data privacy regulations and provide users with control over their personal data.

Important

Privacy compliance is mandatory for EU users under GDPR and represents a critical competitive advantage for building user trust in the health application market.
ID Requirement

FR-4.5.1

Privacy Consent Management: The system shall implement granular consent collection during user registration and onboarding. All consents are stored in the UserConsentEntity table.

FR-4.5.2

Consent Withdrawal: Users shall be able to withdraw previously granted consents at any time through their account settings.

FR-4.5.3

Data Subject Rights (GDPR): The system shall provide mechanisms for users to exercise their GDPR rights, including Right of Access (Article 15), Right to Rectification (Article 16), Right to Erasure (Article 17), and Right to Data Portability (Article 20). These requests are tracked in the PrivacyRequestEntity table.

FR-4.5.4

Privacy Dashboard: The system shall provide a dedicated user interface (PrivacySettingsComponent) for managing privacy settings, viewing consent status, and exercising data subject rights.

FR-4.5.5

Data Processing Logging: All access to and modifications of personal data shall be logged for audit purposes in the DataProcessingLogEntity table, including timestamp, actor, and action details.

FR-4.5.6

Privacy Policy Integration: The system shall prominently display privacy policy information during onboarding and provide easy access throughout the application.

FR-4.5.7

Data Retention Management: The system shall implement automated data retention policies that align with stated privacy policies and legal requirements.

Domain Areas and Business Rules

This section describes the core business domains within the NOM program and the key rules that govern their behavior and data integrity.

User/Person Management Domain

Purpose

Manages individual user accounts and associated personal profiles within the system.

Rule ID Description

Rule-5.1.1

Unique Identification: Each Person record shall have a unique identifier.

Rule-5.1.2

Account Creation: Users must register with a unique email address and a password meeting minimum complexity requirements.

Rule-5.1.3

Email Confirmation: User email addresses should be confirmable to ensure validity and security.

Rule-5.1.4

Password Security: Users must be able to securely reset forgotten passwords and update existing passwords, requiring validation of their current identity.

Rule-5.1.5

Two-Factor Authentication (2FA): Users can opt to enable 2FA for enhanced login security, which requires a one-time code from an authenticator app in addition to their password. The system must support the generation of shared keys and recovery codes.

Rule-5.1.6

Invitation Code Uniqueness: InvitationCodes associated with Person records (for inviting others to join a person-specific context, if applicable) must be unique.

Questionnaire/Onboarding Domain

Purpose

Guides new users through initial data collection to personalize their experience and gather foundational information.

Rule ID Description

Rule-5.2.1

Workflow Sequencing: The onboarding process follows a predefined sequence of steps, leveraging reusable edit components.

Rule-5.2.2

Data Aggregation: All data collected across multiple steps and components during onboarding shall be aggregated into a single, comprehensive payload for final submission.

Rule-5.2.3

Conditional Step Execution: The execution of certain onboarding steps (e.g., additional participant details, individual restriction assignments) is conditional based on prior user input.

Rule-5.2.4

Data Integrity on Navigation: User inputs must be preserved when navigating back and forth through the onboarding wizard.

Plan Management Domain

Purpose

Facilitates the creation, management, and participation in shared nutritional plans.

Rule ID Description

Rule-5.3.1

Plan Uniqueness: Each Plan shall have a unique identifier and a unique InvitationCode (if applicable) for joining.

Rule-5.3.2

Plan Administrator: Every Plan must be associated with a Person designated as its CreatedByPersonId.

Rule-5.3.3

Participant Association: PlanParticipant records define the relationship between a Person and a Plan, and must link to a valid Plan and Person.

Rule-5.3.4

Participant Roles: Each PlanParticipant must have a defined Role (e.g., Admin, Member) governed by a reference data type.

Reference Data Management Domain

Purpose

Provides a centralized, extensible system for managing predefined, static lists and types used across various domains.

Rule ID Description

Rule-5.4.1

Categorization: Reference items are organized into Groups (e.g., "Measurement Type", "Nutrient Type", "Meal Type") to provide context.

Rule-5.4.2

Many-to-Many Association: A Reference item can belong to multiple Groups, and a Group can contain multiple Reference items. This relationship is managed implicitly by the system.

Rule-5.4.3

View Entity Discriminators: Specialized "view" entities (GroupedReferenceViewEntity and its derived types) are used to allow frontend systems to easily filter and categorize reference data by their associated Groups.

Dietary Restriction Management Domain

Purpose

Records and applies dietary constraints for individuals or entire plans to tailor nutritional recommendations.

Rule ID Description

Rule-5.5.1

Association Constraint: Every Restriction must be explicitly linked to either a Person OR a Plan (or both), but not neither.

Rule-5.5.2

Type Definition: Each Restriction must be categorized by a RestrictionType defined in the Reference Data domain.

Rule-5.5.3

Uniqueness per Context: A specific RestrictionType can only be applied once per Person or once per Plan to avoid redundant entries.

Rule-5.5.4

Audit Trail: Every Restriction record must capture who CreatedByPersonId it and CreatedDate.

Data Privacy & Compliance Domain

Purpose

Ensures compliance with applicable data privacy regulations and provides users with control over their personal data.

Warning

GDPR Compliance is Mandatory for EU users. Non-compliance can result in fines up to €20 million or 4% of global revenue, whichever is higher.
Rule ID Description

Rule-5.6.1

Lawful Basis: All personal data processing must have a valid lawful basis under applicable privacy laws (consent, legitimate interest, etc.).

Rule-5.6.2

Consent Documentation: All user consents must be documented with timestamp, version, and specific scope of consent granted.

Rule-5.6.3

Data Minimization: Only personal data necessary for the specified purpose may be collected and processed.

Rule-5.6.4

Purpose Limitation: Personal data may only be used for the purposes explicitly communicated to the user at the time of collection.

Rule-5.6.5

Retention Limitation: Personal data must be deleted or anonymized when no longer necessary for the original purpose, subject to legal retention requirements.

Rule-5.6.6

Security by Design: Appropriate technical and organizational measures must be implemented to protect personal data against unauthorized access, modification, or disclosure.

Rule-5.6.7

Breach Notification: Data breaches affecting personal data must be documented and, where required by law, reported to supervisory authorities and affected individuals within specified timeframes.

Rule-5.6.8

Cross-Border Transfers: Transfer of personal data outside the user’s jurisdiction must comply with applicable legal requirements (Standard Contractual Clauses, adequacy decisions, etc.).

Non-Functional Requirements

Performance

ID Requirement

NFR-6.1.1

Responsive UI: The user interface for the questionnaire should load quickly and respond smoothly to user interactions, minimizing perceived delays.

NFR-6.1.2

Efficient API Calls: Backend API endpoints for fetching questions and submitting answers should respond within acceptable timeframes to ensure a fluid user experience.

Security

ID Requirement

NFR-6.2.1

Data Protection: All sensitive user data (e.g., passwords, personal information, dietary restrictions) shall be transmitted and stored securely.

NFR-6.2.2

Input Sanitization: User inputs shall be properly sanitized and validated to prevent common web vulnerabilities (e.g., XSS, SQL injection).

NFR-6.2.3

Access Control: The system shall enforce proper authorization checks to ensure users can only access data and perform actions they are permitted to.

NFR-6.2.4

Encryption: Personal data shall be encrypted both in transit (TLS) and at rest (database encryption).

NFR-6.2.5

Authentication Security: The system shall implement secure authentication mechanisms including password complexity requirements, account lockout policies, and optional two-factor authentication.

Privacy & Compliance

ID Requirement

NFR-6.3.1

GDPR Compliance: The system shall comply with GDPR requirements for EU users, including data subject rights, lawful basis documentation, and privacy by design principles.

NFR-6.3.2

Consent Management: User consents shall be granular, documented, and easily withdrawable.

NFR-6.3.3

Data Portability: Users shall be able to export their data in a standard, machine-readable format.

NFR-6.3.4

Right to Erasure: The system shall support secure deletion of personal data upon user request, subject to legal retention requirements.

NFR-6.3.5

Audit Logging: All access to and modification of personal data shall be logged for compliance auditing purposes.

NFR-6.3.6

Privacy by Design: Privacy considerations shall be integrated into the system architecture and development process from the outset.

Maintainability & Scalability

ID Requirement

NFR-6.4.1

Modular Architecture: The application shall be built with a modular, domain-driven architecture (both frontend and backend) to facilitate independent development, testing, and deployment of features.

NFR-6.4.2

Consistent Conventions: Strict adherence to naming conventions, coding standards (e.g., BEM for CSS, explicit property assignment in TS constructors), and design patterns to ensure code readability and ease of maintenance.

NFR-6.4.3

Separation of Concerns: Clear boundaries shall be maintained between UI components, business logic (orchestration services), data access layers, and API endpoints.

NFR-6.4.4

Extensibility: The system should be designed to allow for the easy addition of new restriction types and participant management scenarios in the future without significant code refactoring.

Usability

ID Requirement

NFR-6.5.1

Intuitive Workflow: The onboarding process should be easy to understand and navigate for all users.

NFR-6.5.2

Clear Feedback: Users shall receive immediate and clear feedback on their actions, including loading states, validation errors, and submission success/failure messages.

NFR-6.5.3

Responsive Design: The user interface shall adapt seamlessly to various screen sizes and devices (mobile, tablet, desktop) to ensure an optimal user experience.

NFR-6.5.4

Privacy Transparency: Privacy policies and data processing information shall be presented in clear, understandable language.

Technical Naming Conventions & Standards

Important

CRITICAL NAMING RULE: NO MODEL OR DATA TRANSPORT CLASS SHALL EVER USE THE SUFFIX "DTO", "Dto", or "dto". DTO IS STRICTLY FORBIDDEN!

Acceptable Model/Data Transport Suffixes: * Model - For core domain entities and data structures * Request - For inbound API payloads and request objects * Response - For outbound API responses and result objects

Frontend Naming Conventions (TypeScript/Angular)

File Naming

  • Components: kebab-case.component.ts (e.g., person-edit.component.ts)

  • Services: kebab-case.service.ts (e.g., privacy-orchestration.service.ts)

  • Models: kebab-case.model.ts (e.g., onboarding-complete-request.model.ts)

  • Pipes: kebab-case.pipe.ts (e.g., json-parse-common.pipe.ts)

  • Interfaces: kebab-case.interface.ts (e.g., user-consent.interface.ts)

Class/Interface Naming

  • Components: PascalCaseComponent (e.g., PersonEditComponent)

  • Services: PascalCaseService (e.g., PrivacyOrchestrationService)

  • Models: PascalCaseModel/Request/Response (e.g., OnboardingCompleteRequestModel)

  • Interfaces: IPascalCase or PascalCaseInterface (e.g., IUserConsent)

  • Enums: PascalCase (e.g., ConsentType)

Variable/Method Naming

  • Variables: camelCase (e.g., currentStepIndex, userConsents)

  • Methods: camelCase (e.g., submitOnboarding(), withdrawConsent())

  • Constants: SCREAMING_SNAKE_CASE (e.g., API_BASE_URL, MAX_RETRY_ATTEMPTS)

  • Properties: camelCase (e.g., isConsented, consentTimestamp)

  • Controllers: PascalCaseController.cs (e.g., PrivacyController.cs)

  • Services: PascalCaseService.cs (e.g., ConsentManagementService.cs)

  • Entities: PascalCaseEntity.cs (e.g., UserConsentEntity.cs)

  • Models: PascalCaseModel/Request/Response.cs (e.g., DataExportRequest.cs)

  • Interfaces: IPascalCase.cs (e.g., IPrivacyOrchestrationService.cs)

Class/Interface Naming

  • Controllers: PascalCaseController (e.g., PrivacyController)

  • Services: PascalCaseService (e.g., DataAnonymizationService)

  • Entities: PascalCaseEntity (e.g., DataProcessingLogEntity)

  • Models: PascalCaseModel/Request/Response (e.g., ConsentUpdateRequest)

  • Interfaces: IPascalCase (e.g., IConsentManagementService)

Method/Property Naming

  • Methods: PascalCase (e.g., ProcessDataExportRequestAsync())

  • Properties: PascalCase (e.g., ConsentTimestamp, IsConsented)

  • Fields: camelCase or _camelCase for private (e.g., _context, _logger)

  • Constants: PascalCase (e.g., DefaultRetentionPeriod)

Database Naming Conventions

Table Naming

  • Tables: PascalCase matching entity names (e.g., UserConsent, DataProcessingLog)

  • Junction tables: Entity1Entity2 (e.g., PersonPlan, ReferenceGroup)

Column Naming

  • Columns: PascalCase matching property names (e.g., ConsentTimestamp, PersonId)

  • Foreign keys: ReferencedEntityId (e.g., PersonId, PlanId)

  • Primary keys: Id (simple and consistent)

  • Versions: v1, v2 prefix when needed (e.g., /api/v1/privacy/consents)

Key Development Learnings

Angular Development

AOT Compilation

Angular’s AOT compiler is strict. Avoid complex JavaScript expressions directly in HTML template bindings. Move such logic into component TypeScript methods (getters or helper functions).

Standalone Component Imports

Every standalone component must explicitly import all modules it directly uses in its @Component({ imports: […​] }) array. Missing imports cause runtime errors.

Data Flow Patterns

Be mindful of Angular’s unidirectional data flow. Use @Input for data down, @Output for events up. Avoid direct child manipulation.

Template Logic

Use getters in TypeScript for complex template logic (e.g., filteredRestrictionsForCurrentPerson). This resolved "Parser Error: Bindings cannot contain assignments" issues.

Backend Development

API URL Management

Always double-check apiUrl constants in frontend services. These frequently need adjustment between local development and deployment environments.

Interceptor Order

The order of HTTP_INTERCEPTORS in app.config.ts matters. Ensure BearerInterceptor runs before ApiInteractionInterceptor.

Privacy Compliance

Always consider data minimization when adding new data collection points. Document the lawful basis for any new personal data processing.

Debugging Tips

Browser Caching

During frontend development, browser caching can cause issues. Clear browser cache or use "Incognito/Private" mode. ng serve usually handles this well.

Clean Builds

For persistent issues, perform clean builds: npm install, delete .angular and dist directories, then rebuild.

Service Scope Issues

Resolved ServiceScopeFactory reference errors in Program.cs by ensuring proper dependency injection configuration.

Conclusion

This comprehensive business analysis specification provides a complete roadmap for the Nutritional Optimization Machine (NOM) platform development. The document serves as both a technical guide and a compliance framework, ensuring that privacy considerations are built into the system from the ground up.

Key Achievements

Comprehensive Architecture

The specification defines a complete, scalable architecture that separates concerns appropriately while maintaining clear data flow and integration points.

Privacy by Design

GDPR compliance requirements are integrated throughout the system design, from data collection to storage and user rights management.

Clear Development Path

The phased implementation approach provides concrete milestones and deliverables, allowing for iterative development and validation.

Strict Standards

Naming conventions and coding standards ensure consistency and maintainability across the entire codebase.

Strategic Value

Regulatory Compliance

The privacy-first approach positions NOM for successful operation in global markets, particularly the EU where GDPR compliance is mandatory.

User Trust

Transparent data handling and robust privacy controls build user confidence, critical for health applications handling sensitive personal information.

Scalable Foundation

The modular, domain-driven architecture supports future growth and feature expansion without architectural debt.

Competitive Advantage

Privacy compliance as a core feature differentiates NOM in a market where user trust is paramount.

Next Steps

  1. Review and Approval: Stakeholder review of this specification

  2. Team Onboarding: Ensure all developers understand the privacy requirements and naming conventions

  3. Environment Setup: Configure development environments with privacy considerations

  4. Phase 1 Implementation: Begin with critical privacy infrastructure

  5. Iterative Development: Follow the phased approach with regular privacy compliance reviews

The NOM platform is positioned to become a leader in privacy-conscious nutritional planning, setting new standards for how health applications can protect user data while delivering exceptional personalized experiences.
